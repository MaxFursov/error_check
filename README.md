# error_check — бот перевірки товарів «Ділова Ковбаса»

Раз на 2 дні (`CHECK_EVERY_DAYS`) завантажує експорт Проми (`prom_export.xlsx`), шукає помилки в назвах, цінах і даних товарів
та надсилає звіт у Telegram. Про кожну помилку повідомляє **один раз**: наступні звіти містять лише нові.
Якщо помилку виправили, а вона повернулась — повідомить знову.

## Що перевіряється

| Перевірка | Приклад з реального каталогу |
|---|---|
| Змішані кирилиця/латиниця в одному слові | `Cир` (латинська C), `Synnоve` (кирилична о) — на око непомітно, пошук не знайде |
| Вік/тип продукту замість виробника | `Сир … 48% YOUNG` — «Young» це вік сиру, а не ТМ |
| Орфографія та безглузді слова (Claude) | `Camambert`, `Casteiio`, `Нововот роя` |
| Зламані лапки та дужки | `'Баликова"`, `"EDAM 130 г/шт` |
| Занадто коротка назва | `мас`, `шт` |
| *Виведені позиції не перевіряються* | позначені `_ВИВЕДЕНО…` / `Я!ВИВЕДЕНО…` або групою `Я!…` |
| Немає ціни (особливо якщо товар у наявності) | |
| Дублі кодів і назв | |
| Підозріла ціна за кг (ймовірно, ціна пачки) | `Чорізо нарізка 70 г/шт` — 79.96 грн/кг |
| Різка зміна ціни порівняно з минулим запуском | ±40% |
| Архівний товар «в наявності», відсоток > 100 | |
| Дрібниці (лише лічильник і CSV): зайві пробіли, склеєні слова, немає фото | |

Правила працюють без API. Claude (`ai_check.py`) підключається, якщо задано `ANTHROPIC_API_KEY`,
і перевіряє **лише нові або змінені назви** — перший запуск ~2500 назв, далі лише нові.
**Витрати обмежені**: бот рахує реальні токени з відповідей API і не перевищує `AI_MONTHLY_BUDGET_USD` (за замовчуванням $1/місяць) — зупиняється перед порцією, яка б перевищила ліміт, і дочекає наступного запуску/місяця. У кожному звіті є рядок про витрати.
Контекст компанії та список «що не є помилкою» — у `company_context.txt`: додавайте туди нові випадки.

## Чернетки описів

У файлі Проми колонка «Опис» лише дублює назву; справжні описи лежать в «Опис_h2_uk» (HTML: заголовок, склад,
поживна цінність, умови зберігання; у 1С той самий текст вводиться без тегів), заповнено їх лише для ~3% товарів (і майже всі — ковбаси). Бот готує чернетки
**нічого не змінюючи в Промі** (експорт перезаписується з 1С): результат — окремий `descriptions_YYYY-MM-DD.xlsx`
у Telegram (тим самим ботом, що й звіт про помилки).

**Сири (`DESC_ONLY_KINDS=Сир`, `DESC_RESEARCH=true`).** Claude шукає в інтернеті інформацію про сам сир і повертає:
- **розповідь** — 2–5 коротких абзаців: що це за сир (тип, країна, молоко), витримка/жирність/вага, смак і текстура, особливості
  (кристали, скоринка, як подавати), переказаних своїми словами зі сторінок виробників, магазинів і сирних каталогів;
- **дані з етикетки** САМЕ цього продукту, якщо знайшлись: склад, алергени, поживна й енергетична цінність, умови зберігання.

Текст простий (без HTML; 1С сама його розмічає): заголовок, абзаци розповіді, далі блоки етикетки в тому ж порядку, що й у наявних
описах. Нічого не вигадується:
- кожен факт має підтвердження: у режимі API адреси джерел мають бути серед справжньої видачі пошуку; бази користувачів
  (FatSecret, Open Food Facts та ін.), соцмережі й сторінки інших брендів не приймаються;
- розповідь без джерел відкидається; абзаци з рекламою («найкращий», «ідеальний») і медичними твердженнями відкидаються;
- числа етикетки перевіряються на правдоподібність (насичені ≤ жири, кДж ≈ ккал×4,184, сума ≤ 100 г тощо);
- що не знайдено — не потрапляє в текст, а перелічується в колонці «Не знайдено — дописати вручну»; колонка «Джерела» дає
  посилання для звірки. Статус: «повний» (розповідь + вся етикетка) / «розповідь» / «частковий» (лише етикетка) / «лише заголовок».

**Іноземні сири — першими** (`DESC_FOREIGN_FIRST=true`): у назві є латинське слово (бренд), а група не в списку українських
(`DESC_DOMESTIC_GROUPS`). Бренди кирилицею так не розпізнаються — список груп варто підправити.

Важливо: у каталозі зараз **немає жодного опису сиру** — приклад заголовків для сирів задано в `cheese_research.py` і `descriptions.py`
(`STATIC_EXAMPLES`). Знайти точну сторінку вдається не для кожного товару — такі лишаються «лише заголовок».

**Черга без збереженого стану (`--descriptions-prepare --window`).** Для запусків, які не можуть записати файл стану (хмарна
сесія без права запису в репозиторій). Список усіх активних сирів має стабільний порядок (іноземні першими, потім за групами й
кодом). Кожного робочого дня береться наступне «вікно» з `DESC_WINDOW` (30) позицій, відлік від `DESC_START_DATE`; по закінченні
списку — знову з початку. З вікна лишаються сири з порожнім описом у Промі й у наявності. Опис у Промі чи наявність порядок не зсувають,
тому нічого не повторюється й нічого не пропускається; повне коло — близько 26 робочих днів.

**Без пошуку (`DESC_RESEARCH=false`)** — лише заголовок і 2–3 нейтральні речення за назвою, плюс порожній шаблон блоку етикетки.

- Беруться активні товари без опису, спершу в наявності (`DESC_ONLY_IN_STOCK=false` — усі). Раз на `DESC_EVERY_DAYS` днів по `DESC_PER_RUN`.
- **Черга.** Спершу нові (ще не видавані) сири. Якщо їх менше за денну норму — решту добирають **нагадування**: сири, які вже видавали,
  а в Промі опис так і не з'явився (береться з колонки «Опис_h2_uk» свіжого експорту — щойно її заповнили, сир випадає сам).
  Нагадування не частіше ніж раз на `DESC_REMIND_DAYS` (14) днів на сир, без нового пошуку (текст зі сховища); повні й часткові — перед
  «лише заголовок», далі найстаріші першими. У xlsx вони позначені в колонці «Нагадування».
- Чернетки зберігаються в `descriptions.json` поруч зі `STATE_PATH` (потрібен Volume). Файл, який не дійшов у Telegram,
  надішлеться наступного разу; товар, якому вже внесли опис у Пром, випадає сам.
- Окремий бюджет `DESC_MONTHLY_BUDGET_USD`; пошуки теж входять в облік (`AI_PRICE_PER_SEARCH` — перевірте ціну). Вимкнено, доки `DESC_ENABLED=true`.

```bash
python main.py --descriptions --dry-run --limit 5   # покаже зразки й запише reports/descriptions_preview.xlsx
python main.py --descriptions                       # згенерувати й надіслати у Telegram
```

**Без API-ключа (з сесії Claude Code).** Описи й пошук може робити сама сесія Claude, а код лише готує запит і перевіряє відповідь:

```bash
python main.py --descriptions-prepare request.txt        # запит для режиму без пошуку (--codes 1,2,3 — конкретні товари)
python main.py --descriptions-ingest reply.txt           # відповідь «код | ЗАГОЛОВОК | текст»
python main.py --descriptions-ingest-research r.json     # сири: JSON {код: {match, heading, composition, ..., sources}}
```

## Запуск локально

```bash
pip install -r requirements-dev.txt
cp .env.example .env            # заповнити
python main.py --dry-run        # показати звіт, нічого не надсилати і не зберігати
python main.py --dry-run --file prom_export.xlsx
python main.py --once           # одна перевірка з надсиланням у Telegram
pytest
```

## Деплой на Railway

1. Новий проєкт з цього репозиторію (збирається по `Dockerfile`).
2. Змінні середовища — як у `.env.example` (мінімум `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`, `ANTHROPIC_API_KEY`).
3. **Додайте Volume** (напр. на `/data`) і задайте `STATE_PATH=/data/state.json`. Без нього після кожного
   перезапуску бот забуде, про що вже повідомляв, і надішле всі помилки заново.
4. Розклад: перевірка раз на 2 дні о 8:00 за Києвом (`SCHEDULE_HOURS`, `CHECK_EVERY_DAYS`). Дата останньої перевірки зберігається у стані, тож перезапуски не викликають зайвих звітів. При старті бот перевіряє, чи пора (`RUN_ON_START=false` — вимкнути).

## Примітка про формат файлу

У файлі Проми `xl/SharedStrings.xml` написано з великої літери. Excel у Windows цього не помічає,
а на Linux `openpyxl` падає з `KeyError`. `loader.py` перепаковує архів перед читанням (є тест).
Якщо Пром змінить колонки — бот надішле в Telegram алерт про зміну формату.
